# 桶內排序：公式在問什麼問題

> 對應程式碼：`src/match.js`。本文先講公式的**意思**，程式細節放在最後的附錄。

---

## 這個公式想回答的一句話

> **「這筆候選和我的檔案之間，有沒有共用一個『只有它才有』的字？」**

不是「誰跟我最像」，而是「**誰能被指認出來**」。這兩件事在字幕清單裡差很多。

---

## 為什麼不能「數共用幾個字」

同一部片的所有候選**都共用片名**。假設你的檔案是 `Inception.2010.1080p.BluRay.x264-AMIABLE`，
而清單裡有四筆：

| 候選 | 共用的字數 |
| --- | --- |
| `1080p BluRay x264-AMIABLE` | 6 |
| `720p BluRay x264-CROSSBOW` | 4 |
| `CAM Xvid-LKRG` | 2 |
| `TS V2 XVID FEEL-FREE` | 2 |

數共用字數在這裡剛好也對，但問題出在**分數的來源**：`inception` 和 `2010` 貢獻了 2 分，
而它們是**每一筆候選都有的字**——它們證明不了任何事。真正分辨出版本的是 `AMIABLE`，
但在「數數」的算法裡，它跟 `inception` 一樣只值 1 分。

換句話說，數數法讓**沒有資訊的字和決定性的字等值**。當清單裡有一堆名字很像的版本時，
分數高低就取決於「剛好重疊了幾個通用標籤」（`1080p`、`BluRay`、`x264`），
而不是「有沒有命中那個關鍵字」。

---

## 公式

```
一筆候選的分數 = Σ log(1 + N / df)        ← 對「影片檔名也有的每個字」加總
```

| 符號 | 意思 | 白話 |
| --- | --- | --- |
| `N` | 這個語言桶裡有幾筆候選 | 桌上有幾個選項 |
| `df` | 這幾個選項中，有幾個也帶這個字 | 這個字有多普遍 |
| `N / df` | 稀有倍率 | 相對於「人人都有」，這個字稀有幾倍 |
| `log(1 + …)` | 把倍率換算成**份量** | 這個字能提供多少證據 |

拆成三個零件來看：

### 零件一：`N / df` —— 這個字有多稀有

`df / N` 是這個字的**普及率**（0 到 1）。反過來 `N / df` 就是**稀有倍率**：

| 情況 | 普及率 | 稀有倍率 | 白話 |
| --- | --- | --- | --- |
| 每筆候選都有 | 100% | 1 | 一點都不稀有 |
| 一半的候選有 | 50% | 2 | 稍微有指向性 |
| 只有一筆有 | 1/N | N | 最稀有 |

所以 `N/df` 回答的是：**「這個字比『大家都知道的事』稀有幾倍？」**

### 零件二：`log` —— 把「倍率」變成「份量」

這是整個公式最關鍵的一步。

稀有倍率是**乘法**的：`df = 1` 的字的倍率是 `df = N` 的 **N 倍**。
如果直接拿倍率當分數，那麼**一個罕見字就等於 N 個普通字**——
單一個字就能輾壓全場，其他所有證據形同虛設。

取對數之後，倍率從 `1` 到 `N` 的整個範圍，被壓縮成 `log 2` 到 `log(1+N)` 這一段。
於是每個字都是**「一份可累加的證據」**，而不是「一個可以輾壓全場的倍數」。

> **證據要能累加，不能互相輾壓。**

這個直覺和資訊理論一致：意料之中的訊息帶來的資訊量趨近 0，
意料之外的訊息資訊量大；而且**資訊量是可加的**。
「片名」是意料之中（大家都知道），「發行組」是意料之外（只有它知道）。

### 零件三：`1 +` —— 一個小地方

`1 +` 讓「人人都有的字」得到 `log 2` 而不是 `log 1 = 0`。
它對**排序沒有影響**——因為所有候選都被墊高了同樣的常數。
它的作用是讓分數讀起來是「證據總量」而不是「超額證據」，
也避免 `df = N` 這種情況掉進 `log(1) = 0` 的退化。

---

## 份量有多大？一張表看懂

| 這個字有幾個候選也有 | N = 4 時的份量 | N = 10 時的份量 | 白話 |
| --- | --- | --- | --- |
| 全部（= N） | 0.69 | 0.69 | 「大家都知道的事」 |
| 一半 | 1.10 | 1.70 | 「稍微有指向性」 |
| 只有它（= 1） | 1.61 | 2.40 | 「幾乎可以指認」 |

兩件事值得注意：

1. **「大家都知道的事」份量固定是 0.69**，不管有幾個候選。它永遠是最小的那一份。
2. **候選越多，罕見字的份量越大**（1.61 → 2.40）。選擇越多，「只有它有」這件事越不可能是巧合。

---

## 分數的意思

**分數 = 這筆候選能提出的證據總量。**

它本身**沒有絕對意義**——沒有「幾分以上才算對」這種事。它唯一的用途是**排序**。
所以不需要任何門檻或校準，換一批候選、換一部片，份量自動重算。

而分數的高低主要由**最稀有的那些共用字**決定，因為它們的份量最大。
這就是為什麼這個公式不需要維護任何「發行組／編碼器／片源類型」的清單——
它不認識 `AMIABLE` 是什麼，它只知道「這個字只有一筆候選有，而且你的檔案也有」。

---

## 具體例子：把份量一項一項列出來

影片 `Inception.2010.1080p.BluRay.x264-AMIABLE.mkv`，四筆候選。

**候選 `1080p BluRay x264-AMIABLE`（正確的那筆）**

| 它說的字 | 有幾個候選也說 | 份量 |
| --- | --- | --- |
| inception | 4 / 4 | 0.69 |
| 2010 | 4 / 4 | 0.69 |
| bluray | 2 / 4 | 1.10 |
| x264 | 2 / 4 | 1.10 |
| 1080p | 1 / 4 | 1.61 |
| amiable | 1 / 4 | 1.61 |
| **合計** | | **6.80** |

**候選 `CAM Xvid-LKRG`（錯的那筆）**

| 它說的字 | 有幾個候選也說 | 份量 |
| --- | --- | --- |
| inception | 4 / 4 | 0.69 |
| 2010 | 4 / 4 | 0.69 |
| **合計** | | **1.39** |

它還有 `cam`、`xvid`、`lkrg` 這些獨有的字，但**影片檔名裡沒有這些字，所以完全不加分**。

### 這個例子說明了什麼

正確的那筆，光靠「片名 + 年份」只拿到 **1.39**；
而「`1080p` + `AMIABLE`」這兩個字單獨就給了 **3.22**——是前者的兩倍多。

**辨識版本的字，份量遠大於大家都知道的事。** 這就是整個公式的目的。

## `✓` 的門檻：`rareLimit`

```
rareLimit = ceil(N / 3)
```

一個字要被當成「足以指認」，它必須**不被超過三分之一的候選擁有**。

| 候選數 N | rareLimit | 白話 |
| --- | --- | --- |
| 1 | 1 | 沒得比較，任何共用字都算 |
| 4 | 2 | 只有 1～2 筆候選有的字才算「指認」 |
| 10 | 3 | 只有 1～3 筆候選有的字才算「指認」 |

候選越多，標準越嚴——因為「只有少數人有」在選項多的时候更不可能是巧合。

`✓` 只標在**第 1 名**，而且它必須符合這個門檻（或是 hash 命中）。
若清單只有 1 筆，就不標——沒有可選的對象，標了不帶資訊。

---

## 這個公式不做的事

- **不判斷哪個版本比較好。** 它不認為 BluRay 比 CAM 好，只回答「哪個跟你手上的檔案最可能是同一版」。
- **不設及格線。** 沒有任何「低於幾分就丟掉」的規則；取幾筆完全由 `perLanguageLimit` 決定。
- **沒有檔名就完全不作聲。** 沒有影片檔名就沒有共同的字可比，所有候選同分，排序退化成上游原始順序，`✓` 也不會出現。
- **不偏袒任何來源。** 分數只看版本名稱，不看是哪個外掛提供的。

# 附錄：實作細節

## 切 token 的三個過濾條件

```js
String(name).toLowerCase()
  .replace(/[._\-+[\]]+/g, ' ')   // 點、底線、連字號、加號、方括號 → 空白
  .split(/[^a-z0-9]+/)
  .filter((t) => t.length >= 3 && !NOISE.has(t) && !LANGUAGE_TAGS.has(t));
```

| 條件 | 理由 | 例子 |
| --- | --- | --- |
| `length >= 3` | 兩字母標記資訊量太低、雜訊多 | `TS`、`V2` 被丟掉 |
| 不在 `NOISE` | 副檔名／容器格式無法識別版本 | `srt`、`mkv`、`www` |
| 不在 `LANGUAGE_TAGS` | 語言標記識別的是**翻譯**而非**版本** | `cht`、`eng`、`dual` |

標點一律當分隔符，因為發行名稱混用它們——`x264-AMIABLE` 與 `x264.AMIABLE` 是同一版。

## 排序與同分

```js
scored.sort((a, b) => b.score - a.score || a.index - b.index);
```

分數高的在前；**同分時維持上游原始順序**。既然沒有證據分出高下，就不自作主張重排。

## 完整驗算

以實際程式碼執行上述例子：

```
video tokens: inception, 2010, 1080p, bluray, x264, amiable
df: 2010=4 inception=4 bluray=2 x264=2 xvid=2 1080p=1 ... amiable=1 crossbow=1
rareLimit: 2
  #2 score=6.802 distinct=true  | ...1080p.BluRay.x264-AMIABLE
  #3 score=3.584 distinct=true  | ...720p.BluRay.x264-CROSSBOW
  #0 score=1.386 distinct=false | ...CAM.Xvid-LKRG
  #1 score=1.386 distinct=false | ...TS.V2.XVID.FEEL-FREE
```

後兩名同分 → 維持原始順序（#0 在 #1 前）。取前 3 筆，`✓` 標在第 1 名。
`CROSSBOW` 雖然也符合 `distinct`，但不是第 1 名，所以不標。
